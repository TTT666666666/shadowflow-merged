# 诊断引擎评测（2026-11）

> 这份文档回答一个问题：**没有模型，这套规则引擎的质量到底是多少。**
> 结论先说：它不做推理，它是筛查。它的质量用「误杀率 / 漏放率」衡量，不用「推理能力」衡量。

## 1. 这次评测发现了什么

我用 24 条真实形态的商品文案跑了一遍引擎，发现 **5 个真 bug**，其中 3 个会直接把合规商品判成「不可上架」。

| # | 问题 | 后果 | 状态 |
|---|---|---|---|
| 1 | `_as_list` 用 `lstrip("-•*0123456789.、) ")` 剥列表符号 | 卖点开头的数字被吃：`100%纯棉`→`%纯棉`、`500ml`→`ml`、`32支精梳棉`→`支精梳棉`、`7天无理由`→`天无理由`。材质/规格/发货三类规则集体失明 | 已修 |
| 2 | `100%` 被列为极限词 | `100%纯棉`、`100%桑蚕丝`、`100%果汁` 全被判违规下架 | 已修（按后接词判语境） |
| 3 | `美白 / 祛斑` 记 high | 美白精华被判「不可上架」，整个美白品类被误杀 | 已修（拆成 medium「需注册证号」+ high「效果承诺」） |
| 4 | `食品级` 记 high | 儿童硅胶水杯、辅食碗被判「不可上架」，母婴最常用的合规表述成了违禁词 | 已修（移入正向材质词） |
| 5 | `有机 / 绿色食品 / 非转基因` 记 high | 正规有机食品被判违规 | 已修（拆成 medium「需证书编号」） |

另外发现一处**自相矛盾**：`终身保修 / 无效退款 / 零风险` 与 `保证有效 / 包治` 被塞进同一个词表、同一个 medium 档，结果前者被过度宽容、后者被过度宽容。已拆成「效果保证（high，进合规门禁）」和「服务承诺（medium，只提示）」。

### 修前修后（同一条文案）

| 案例 | 修前 | 修后 |
|---|---|---|
| 烟酰胺美白精华液 | 59 分 · **不可上架** | 76 分 · 可上架（提示补「国妆特字」编号） |
| 儿童硅胶折叠水杯 | 59 分 · **不可上架** | 81 分 · 可上架 |
| 100%纯棉T恤 | 78 分（100% 被吞，侥幸放过） | 78 分（正确豁免） |

有意思的是 A01：修完 bug 1 之后它从 78 掉到 59——因为 `100%` 终于能被看见了，然后被 bug 2 判死。**修一个 bug 会暴露下一个 bug**，这就是为什么必须有可复跑的回归集，而不是靠人工抽查。

## 2. 回归集指标

复现命令：

```bash
python scripts/eval-listing-doctor.py
python -m pytest tests/test_listing_golden.py tests/test_listing_engine_quality.py -q
```

| 指标 | 结果 | 含义 |
|---|---|---|
| 放行准确率 | 14/14 = 100% | 合规商品没被误拦 |
| 拦截准确率 | 10/10 = 100% | 违规文案没被放过 |
| 关键码召回 | 12/12 = 100% | 该抓的关键词抓到了 |
| 误杀码次数 | 0 | 声明不该出现的码一次都没出现 |
| 判定总准确 | 24/24 = 100% | — |

### 这组数字不能证明什么（重要）

**它不能证明准召率是 100%。** 这 24 条是我按引擎的行为设计的、标签是我自己标的，全过是必然的。它能证明的只有两件事：

1. 已知类型不会被判错（不会误杀美白、纯棉、食品级、有机）；
2. 以后的改动不会让这些判定退化（回归锁）。

真实准召需要**第三方标注的真实 listing**：100 条以上、覆盖 8 个品类、由运营或法务判定「这条有没有问题、是哪一条」。这个数据集我没有，也不该由我编。

## 3. 已知缺陷（写进测试的 xfail，不假装不存在）

| 缺陷 | 例子 | 现在会怎样 |
|---|---|---|
| 否定语境不识别 | 「我们不是全网最低价」 | 仍命中极限词 → 误杀 |
| 词表外漏报 | 「性价比最高」「买到就是赚到」 | 不含词表词 → 放过 |
| 暗示性功效漏报 | 「帮助身体回到平衡状态」「让你慢慢好起来」 | 不含功效词 → 放过 |
| 医疗器械弱宣称漏报 | 「缓解酸痛」 | 「缓解」不在词表 → 放过 |
| 拆字/拼音规避 | 「最~好」「全网zui低价」 | 检不出 |

这些用 `@pytest.mark.xfail` 标在 `tests/test_listing_engine_quality.py` 里。它们在 pytest 输出里显示为 `4 xfailed`，谁都能看到还剩几条；哪天真补上了会变成 `XPASS`，提醒把标记删掉。

**第 1 条是误杀，后 4 条是漏放。** 在合规场景，漏放比误杀危险——误杀会让用户觉得工具笨，漏放会让用户被罚。所以这 5 条的优先级不一样。

## 4. 天花板在哪

规则引擎能做的是**「已知风险模式的确定性检出」**：

- 词表内的极限词、功效词、类目违禁表述；
- 结构性缺失（没有材质、没有售后、没有 CTA、卖点条数不对）；
- 平台硬限制（标题字数、五点条数、促销语、联系方式）；
- 可计算的语境（`100%` 后接成分还是效果）。

它做不到的是**「读懂」**：

- 判断这段文案整体有没有说服力、像不像人写的；
- 判断卖点排序符不符合买家决策路径；
- 判断一句没有违禁词的话是不是在暗示疗效；
- 处理反讽、否定、拆字、谐音。

所以它的正确身份是**上架前体检**，不是商品诊断。体检的价值是「不漏项、可复现、便宜到能天天做」，不是「诊断得多聪明」。

## 5. 下一步（按是否需要模型分）

**不需要模型：**
- 把「缺陷（写了但写错）」和「缺项（还没写）」在报告里分开。现在 `price.no_bundle`（没赠品）、`cta.no_contact`（没留联系方式）几乎每条都中，把合格文案压到 65-78 分，噪音淹没了真问题。
- 扩真实样本：需要 100 条脱敏的真实 listing 才能算准召。

**需要模型：**
- 混合架构：规则负责召回（零成本、高召回），只把命中的 5-8 项连同原文喂模型一次，让它排序、写人话解释、判断暗示性表述。成本约为全文盲评的 1/10，且模型不用自己找问题，幻觉风险小。
- `analyze(payload, enhance=...)` 的钩子已经留好，但**目前 API 未接线**，`engine` 恒为 `rules`。接模型时只需实现一个 provider 并传进去，不改判定口径。
